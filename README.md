# 兵棋多智能体协同

在同一个 SDK 世界内运行红蓝双方多个独立策略实例。各实例有自己的席位、棋子、局部观测、敌情记忆和消息处理状态。协调器负责分配与调度，具体动作由各专业智能体生成。

## 运行

```bash
conda run --no-capture-output -n wargame python run_offline_games.py
```

默认采用 `1930331196` 的兵种模板和 `map_96`，启动时生成双方合计 **500 枚棋子、20 个智能体**的对称对抗。每方 250 枚、10 个智能体；这里统计的是棋子数量，不是血量/车班数。完整运行到 SDK 返回 `done=True`。

| 每方职责 | 智能体数量 | 每个控制棋子数 | 兵种配比 |
| --- | ---: | ---: | --- |
| 突击 | 4 | 30 | 坦克 60、战车 60 |
| 夺控 | 4 | 25 | 人员 60、无人战车 40 |
| 支援 | 2 | 15 | 炮兵 12、无人机 10、武装直升机 8 |

红方席位为 1–10，蓝方为 101–110；每方仅第一个席位拥有指挥角色。按兵种及部署列坐标分区均衡分配，战斗中保持归属稳定，避免移动后不断更换智能体。

初始部署：红方位于地图北侧第 13–29 行，蓝方位于南侧第 62–78 行（坐标从 0 开始）。装甲在前，人员/无人战车居中，炮兵与航空单位在后；双方位置旋转 180 度对应，初始地形类型相同。每格初始仅一枚棋子，地面单位所在区域与目标点存在通行连接。双方均为已展开的地面兵力，人员、无人战车仍保留与有人战车的隶属关系；没有为凑数放置悬空的载员或巡飞弹。

地图中央设置 8 个中立据点，各群按区域行动；突击和夺控预备兵力在据点后方分散集结，减少所有单位同时堵在据点中心。部署前检查可通行性、可用格数量、模板兵种、ID 与总数，条件不满足则明确报错。地形并非完全对称，镜像部署不代表绝对相同的进攻难度。

源想定 JSON 不会被覆盖；每次实际生成的部署保存在运行目录的 `initial_deployment.json`。

```bash
# 默认 500 枚棋子的快速验证；输出会标记 truncated=true
conda run --no-capture-output -n wargame python run_offline_games.py --max-steps 120
# 使用源想定兵力，不扩充棋子
conda run --no-capture-output -n wargame python run_offline_games.py --units 0 --scenario 2110431553 --map 53
```

`--seed` 只设置 AI 寻路的随机平局选择，不固定 SDK 战斗裁决的随机数。

## 控制与共享

大规模模式下，突击为红 1–4 / 蓝 101–104，夺控为红 5–8 / 蓝 105–108，支援为红 9–10 / 蓝 109–110。`--units 0` 时每方保留三个专业智能体。

一方仅首个席位为指挥角色（role=1），其他席位为队员（role=0）。初始化后通过指挥席位提交 SDK 的编组动作 `100`，再由各席位提交结束部署动作 `333`。后续只有归属发生变化时才提交新的编组动作。

每个智能体根据 SDK 的 `role_and_grouping_info` 确定控制权，不再根据兵种自行认领同阵营棋子。该智能体能读取自己全部棋子和乘员的 SDK 信息，汇总其所控活动棋子的可见敌军。其他席位的单位状态和敌情通过消息共享。双方共用一个 TrainEnv，以保持同一对局状态；不需要为每个智能体创建独立世界。

每帧按“全部智能体观察 → 发布信息 → 消费消息并独立决策”执行。当前在一个进程中顺序调度。

消息按 `阵营:席位` 寻址（同兵种不同智能体也使用独立收件箱），负载深拷贝，处理分支包括：

- `enemy_spotted`：共享实际观察到的敌军位置、血量、兵种和时间；用于威胁评估和支援目标规划。
- `unit_status`：共享己方单位位置和血量；供支援跟随及间瞄避开已知友军位置。
- `support_request`：夺控单位请求掩护；突击与支援智能体据此选择掩护目标。
- `action_intent`：通报本帧的射击目标或夺控点，减少重复射击与重复夺控。

单位状态每 10 步共享、敌情每 5 步共享，掩护请求与动作意图仍随决策发送。消息按帧写入日志后释放历史副本，避免大规模长对局积累内存。敌情保留 30 个步长。传来的敌情不赋予射击权；直瞄和引导射击仍必须来自 SDK 当前合法动作候选。

## 规则对应

以 `wargame_rule.md` 为战术规则参考，以 `开发文档.md` 为 SDK 接口参考：

- 第三部分第 1 节：不重复提交进行中的机动，路径避开已知路障；炮兵不生成机动动作。
- 第 5 节：取消“距离据点 5 格即可夺控”的旧判断，依据 SDK 的夺控合法性执行。
- 第 7、8 节：保留实际观察限制；由 SDK 判定射程、武器展开、冷却、压制等约束，允许 SDK 判定合法的坦克行进间射击。
- 第 9 节：间瞄使用共享敌情；若已知友军位于目标本格或相邻格则暂缓。该检查不能消除未来友军移动、炮火散布等导致的误伤。
- 第 10 节：携带巡飞弹的车辆通过合法下车/发射候选释放巡飞弹，发射后由支援席位控制。

这些规则不包含席位 API 的定义；席位和编组接口来自开发文档，已经在随附 SDK 4.1.0 中验证。

## SDK 4.1.0 兼容

实测发现 `TrainEnv.step()` 返回的观测中，部分字段仍沿用初始态势，不能据此断言编组或结束部署失败。`run_offline_games.py` 内的 `SDKAdapter` 将这一兼容处理集中在一处：提交动作仍用 `TrainEnv.step()`，随后只读调用 `engine.get_sd_data()` 获取最新的红、蓝、全局观测。

业务智能体和协调器均不访问 SDK 引擎。运行器自行流式保存回放，在 SDK 自带回放保存关闭时只保留其最近的冗余回放缓存，避免 500 枚棋子的历史态势占满内存；该清理不改变推演状态。代码不再修改 `clock.stage`，不再调用内部 `assign_operators()`，也不再从全局回放中拼造阵营观测。由于此版本的观测问题，适配层仍有这一处对引擎读取接口的依赖。

`ai/agent.py` 保留旧集中式策略供参考，当前入口只使用 `Coordinator` 和三个专业策略类。

## 回放与审计

每次运行生成：

- `logs/replays/replay_<运行编号>.zip`：平台回放，全局态势只用于回放和离线核验。
- `logs/runs/<运行编号>/summary.json`：步数、是否正常结束、SDK 兵力编组、各席位动作及错误统计。
- 同目录 `initial_deployment.json`：本次实际兵力与初始坐标。
- 同目录 `decisions.jsonl`：各席位控制列表、自己发现的敌情、已知敌情、目标和输出动作。
- 同目录 `messages.jsonl`：消息发送者、接收者、类型及内容。

此前已使用临时检查核验 SDK 归属、越权动作、敌情来源和阵营隔离，结果保留在运行目录的 `verification.json` 中。按要求，新增的测试和核验 Python 文件现已删除，必要的运行逻辑均保留在原有 Python 文件内。

完整实测对比见 `docs/修复验证报告.md`。SDK 按顺序裁决同帧动作，仍可能拒绝观测后已被其他动作击毁棋子的指令，这类错误会原样保留在审计中。
